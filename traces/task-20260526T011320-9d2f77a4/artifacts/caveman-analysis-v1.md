# Caveman Analysis: Robot Fleet Ops Dashboard

## Plain-Language Explanation

人形机器人散布在各处干活。运维工程师需要一块屏幕，一眼看到所有机器人的健康状况。

面板做的事：
1. **接收数据** — 每台机器人不停发回自身状态数据。问题：不同机器人说的"语言"不一样（字段名不同，单位不同）。面板先翻译成统一语言。
2. **展示数据** — 大屏总览显示整体健康度（圆环、曲线、热力图）。点击某台机器人进入详情。
3. **发出警报** — 机器人摔倒/关节断联/电量太低 → 自动通知。
4. **翻阅历史** — 过去 30 天任何指标的变化曲线。
5. **调整设置** — 工程师可以改每台机器人的报警阈值、采样快慢、断线重连策略。
6. **同事协作** — 在某台机器人下面留言、@同事、标记"我在处理"。
7. **导出报表** — 一键生成 PDF 或 Excel。
8. **自定义外观** — 暗色/亮色、多语言、拖拽面板布局。

## Minimum Viable Version

最简可工作版本只需要：
- 一个页面，列出所有机器人（卡片列表）
- 每张卡片显示：名字、电量条、连接状态（绿/黄/红）、最后上报时间
- 点击卡片 → 展开详情（关节温度表、CPU、当前任务）
- 三个硬编码告警规则（摔倒/关节失联/低电量）
- 数据归一化层做字段映射（不做完整 protobuf 解析，mock 数据即可）
- 暗色/亮色切换

**这 6 样东西跑通后，其余都是增量：** 图表库接入 → 历史曲线 → 协作 → 导出 → 多语言 → 拖拽布局。

## Complexity Assessment

### Justified Complexity
- **异构数据归一化层** — 这是核心工程挑战。不同机器人厂商/版本数据格式不同，不统一后续全链条都没法做。必须投入。
- **时序数据存储** — 30 天历史需要专门的时序方案（InfluxDB / TimescaleDB / 客户端聚合），不能简单丢 PostgreSQL。
- **WebSocket 实时推送** — 运维面板不同于普通 CRUD 应用，数据是持续推送的，前端需要流式订阅架构。

### Unnecessary Complexity (可简化)
- **多语言 (i18n)** — Demo 阶段只做中/英文切换框架，不翻译全部文案。框架到位即可。
- **可拖拽布局** — Demo 阶段预设 2-3 种布局模板（紧凑/宽松/专注），不做完整拖拽引擎。react-grid-layout 接入即可，不分精力定制。
- **完整 protobuf 解析** — Demo 阶段用 JSON mock 数据，protobuf 适配器留接口。归一化层的 schema registry 设计到位就行。
- **PDF/Excel 导出** — Demo 阶段导出 CSV（浏览器端），不接入服务端渲染 PDF。
- **RBAC 权限** — 留注释，不实现。

## So What

车队监控的本质是：**数据归一化 + 实时推送 + 告警规则引擎**。这是核心价值。图表、协作、导出都是提升体验的壳。Demo 应该证明核心链路跑通，而非展示所有壳。
