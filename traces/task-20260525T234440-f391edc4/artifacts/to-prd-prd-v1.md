# PRD — 机器人车队运维监控面板 (FleetOps Dashboard)

> 版本: v1.0 | 状态: ready-for-agent | 来源: triage + caveman 分析

---

## Problem Statement

运维工程师管理着一批人形机器人车队。每台机器人通过各自的固件回传状态数据（电量、关节温度、CPU 负载、网络延迟、当前任务、GPS 位置），但这些数据**格式不统一**：有的厂商用 JSON，有的用 Protobuf 衍生格式，字段命名和计量单位也不一致。工程师需要在多套工具之间来回切换才能看清整个车队的健康状况。当机器人出现摔倒、关节失联、电量过低等异常时，缺乏统一的告警通道，响应时间被拉长。此外，工程师之间缺少围绕具体机器人的协作机制，导致重复排查。团队还需要历史数据回溯和合规报表导出。

## Solution

一个 Web 单页应用（SPA）运维面板，提供 **统一数据视图、实时告警、历史回溯、团队协作、可配置阈值、报表导出** 六大能力。面板通过数据归一化层将异构数据源转为统一 schema，以卡片网格展示车队总览，以多种图表展示健康度分布与趋势，以 WebSocket 推送异常告警，以时间序列数据库支撑 30 天历史查询，以内嵌协作功能支持留言/@/认领，以配置面板让工程师按机器人独立调整参数，支持暗色/亮色主题、多语言和可拖拽布局。

## User Stories

### 核心监控 (P0 — 无此则不可用)
1. 作为运维工程师，我想在一屏内看到所有机器人的在线状态、电量和告警数量，以便快速判断车队整体是否正常。
2. 作为运维工程师，我想点击任意机器人卡片查看其完整遥测数据（电量、关节温度、CPU、网络延迟、当前任务、位置），以便深入排查。
3. 作为运维工程师，当机器人摔倒/关节失联/电量过低时，我想立即看到红色告警弹窗并听到声音提示，以便在 5 秒内开始响应。
4. 作为运维工程师，我想看到机器人过去 30 天的电量/温度/CPU 历史曲线，以便判断异常是突发的还是渐近恶化的。

### 数据可视化 (P1)
5. 作为运维工程师，我想在总览面板看到环形图（车队健康度占比）、折线图（近 1 小时趋势）、热力图（地理位置分布），以便从不同维度理解车队状态。
6. 作为运维工程师，我想可以按机器人分组、区域、任务类型筛选仪表盘数据，以便聚焦特定子集。

### 告警与通知 (P0)
7. 作为运维工程师，我想按机器人独立配置告警阈值（例如 A 机器人关节温度 > 65°C 告警，B 机器人在高温环境中阈值设为 75°C），以便减少误报。
8. 作为运维工程师，我想看到告警历史列表（时间、机器人、类型、级别、是否已处理），以便追踪响应效率。
9. 作为运维工程师，当告警被处理后，我想手动标记为「已处理」并填写处理备注，以便团队交接。

### 配置管理 (P1)
10. 作为运维工程师，我想为每台机器人独立调整采样频率和重连策略，以便在关键任务期间提高数据密度，在普通任务期间节约带宽。
11. 作为运维工程师，我想批量选择多台机器人并统一修改配置，以便快速部署策略变更。

### 团队协作 (P1)
12. 作为运维工程师，我想在任意机器人下方留言（如「左膝温度偏高，已通知现场」），以便团队共享排查进展。
13. 作为运维工程师，我想在留言中 @ 同事（如 @张三 请确认网络延迟），以便精准通知相关人。
14. 作为运维工程师，我想点击「我在处理」来认领一台异常机器人，以便其他同事看到后不再重复介入。

### 报表与导出 (P2)
15. 作为运维经理，我想导出指定时间范围和机器的 PDF 报表，以便在周会上展示车队运营状况。
16. 作为运维经理，我想导出 Excel 格式的原始数据，以便在外部工具中做进一步分析。

### 个性化 (P2)
17. 作为运维工程师，我想切换暗色/亮色主题，以便在 7×24 轮班中保护视力。
18. 作为运维工程师，我想将界面切换为中文/英文，以便在不同团队中使用。
19. 作为运维工程师，我想拖拽调整卡片和图表的位置和大小，以便适配自己的工作习惯和屏幕尺寸。

## Implementation Decisions

### 1. 数据归一化层 (Data Normalization Layer)
- **独立微服务**，部署在数据接入和后端之间
- 输入：异构原始数据流（JSON / Protobuf / 自定义二进制）
- 输出：统一 `RobotTelemetry` schema（所有下游消费同一结构）
- 归一化策略由 **adapter 模式** 实现：每种数据源一个 adapter，热加载
- 单位转换在此层完成（华氏→摄氏、英里→公里 等）
- Schema:
```
RobotTelemetry {
  robot_id: string (必填)
  timestamp: ISO8601 (必填)
  battery_pct: float (0-100)
  joint_temps: map<string, float>  // joint_name → celsius
  cpu_pct: float (0-100)
  network_latency_ms: int
  current_task: string | null
  gps: {lat: float, lon: float} | null
  status: ONLINE | OFFLINE | WARNING | ERROR
}
```

### 2. 实时数据通道
- **WebSocket** 长连接，服务端主动推送
- 数据流：Robot → Gateway → Normalizer → Kafka → WebSocket Server → Browser
- 心跳间隔可配置（默认 5s），超时 > 15s 标记为 OFFLINE
- 前端使用共享 WebSocket 连接，按 robot_id 做 client-side routing

### 3. 告警引擎
- 基于规则引擎（非 ML），运行在 Backend
- 每条新遥测数据进入时触发规则评估
- 规则结构：`{condition: "battery_pct < threshold", severity: WARNING|CRITICAL, robot_id: "*"|specific}`
- 阈值从配置面板读取，实时生效
- 告警去重：同一机器人同一告警类型在 5 分钟内只发一次
- 告警通道：WebSocket 推送 + （可选）Webhook/SMS 集成

### 4. 历史数据存储
- **时序数据库**：InfluxDB 或 TimescaleDB
- 保留策略：30 天原始精度，30-90 天降采样（1 分钟聚合）
- 查询 API 支持时间范围、机器人 ID、指标类型、聚合粒度

### 5. 前端架构
- **React + TypeScript**，状态管理 Zustand
- 图表库：ECharts（环形图、折线图、热力图）
- 地图组件：Mapbox GL JS 或 Leaflet（GPS 热力图）
- 拖拽布局：react-grid-layout
- 主题：CSS Variables + 全局主题切换
- i18n：react-i18next

### 6. 协作功能
- 留言系统内嵌于机器人详情面板
- 数据模型：`{message_id, robot_id, author, text, mentions: [], timestamp}`
- 「我在处理」状态：`{robot_id, claimed_by, claimed_at, expires_at}`
- 认领超时自动释放（默认 30 分钟）

### 7. 报表导出
- PDF：服务端渲染（Puppeteer / wkhtmltopdf）或前端 canvas 截图
- Excel：后端生成 xlsx，CSV 备选

## Testing Decisions

### 测试策略
- **只测试外部行为，不测试实现细节**
- 测试金字塔：单元测试（数据归一化、告警规则）> 集成测试（WebSocket 通道、历史查询 API）> E2E（核心用户旅程）
- 不测试：CSS 样式细节、拖拽动画、图表像素

### 关键测试场景
1. 数据归一化层：输入 5 种异构格式，验证输出统一 schema
2. 告警引擎：模拟电量 15%（低于阈值 20%），验证 CRITICAL 告警触发 + WebSocket 推送
3. WebSocket 重连：断开网络 30 秒，验证自动重连 + 数据补推
4. 历史查询：写入 30 天模拟数据，验证查询响应 < 2s
5. 认领冲突：两个用户同时认领同一机器人，验证只有一人成功
6. 主题切换：所有图表和组件在暗色/亮色下均可读
7. 拖拽布局持久化：刷新页面后布局保持

## Out of Scope

- 机器人远程控制/指令下发（本面板只读）
- 移动端 App（仅 Web）
- 用户认证/权限系统（假定已有 SSO 集成）
- 计费/订阅管理
- 固件 OTA 更新
- 自然语言查询（如"哪些机器人快没电了"）
- 视频/摄像头实时流
- 第三方系统集成（Slack/PagerDuty）— 通过 Webhook 预留接口，但不实现

---

## Success Criteria

1. 同时展示 50 台机器人实时数据，更新延迟 < 2 秒
2. 异常告警从遥测到达到浏览器弹窗 < 5 秒
3. 历史曲线查询 30 天数据 < 2 秒返回
4. 异构数据源新增（新机型加入）仅需新增一个 adapter，不修改核心代码
5. 暗色模式下所有图表和文字保持 AA 级可读性（WCAG 2.1）
6. 90% 运维工程师能在首次使用后 10 分钟内独立完成以下操作：定位异常机器人、查看历史曲线、标记告警已处理

## Open Questions

1. 车队规模上限是 50 台、200 台还是 1000 台？（影响 WebSocket 连接池和前端渲染策略）
2. 异构数据源具体有多少种？举例 2-3 种即可确定 adapter 抽象粒度
3. 是否有现有 SSO 系统？OAuth2 / LDAP / SAML？
4. 报表需要包含哪些具体指标？是否有时段对比功能？
