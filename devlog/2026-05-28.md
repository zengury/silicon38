# Devlog — 2026-05-28

## 主题：Silicon Org 融合 LangGraph，进入可执行代码开发组织形态

今天的目标不是继续讨论架构，而是把 Silicon Org 从“协议 + 图谱 + 账本”的设计推进到可本地运行、可验证、可进入业务任务的版本。

核心结论：

> Silicon Org 的主业务范围应聚焦在复杂软件工程交付：把模糊需求推进到可审计、可验证、可学习的代码开发流程。

LangGraph 在这个版本里不是 Silicon Org 的大脑，也不是替代 Graph/Policy/Ledger/Learning。它是执行内核。Silicon Org 继续拥有组织定义、节点 harness、权重图谱、账本事实、上下文链和学习机制。

## 完成了什么

### 1. LangGraph-native runtime 内核

新增并推进了 LangGraph-native runtime：

- `runtime/langgraph_native.py`
- `runtime/harness_profiles.yaml`
- `requirements-langgraph-oss.txt`
- `pyproject.toml` 的 `langgraph-oss` optional dependency
- `docs/LANGGRAPH_NATIVE_RUNTIME.md`

运行拓扑被收敛为稳定内核：

```text
START
  -> encoder
  -> policy_router
  -> run_role_node
  -> policy_router
  -> convergence_policy
  -> graph_topologist_node
  -> learning_engine_node
  -> END
```

注意：这里没有缩减 Silicon Org。35 个组织节点仍然完整存在于：

- `ontology/nodes.yaml`
- `ontology/relations.yaml`
- `runtime/harness_profiles.yaml`

LangGraph 只承载 durable execution、dynamic send、状态合并和循环恢复边界。节点激活仍由 Silicon Policy 读取 weighted graph 动态决定。

### 2. 35 个节点全部映射到 harness profile

每个节点都拥有独立的运行配置可能性：

- purpose
- model profile
- tool groups
- write scope
- resource budget
- input/output contract
- completion gates

具体模型 ID 不写死在 graph 中。默认使用 runtime 当前模型；未来每个节点可以通过 `org/models.local.yaml` 单独配置。

### 3. Ledger-backed node runtime

新增 Ledger transaction 层：

- `runtime/ledger_transactions.py`
- `runtime/node_runner.py`

LangGraph 节点不再散落写 YAML，而是通过 Ledger transaction 提交事实：

- task init
- node activation
- handoff
- artifact registration
- context report registration
- node completion
- delivery outcome
- learning snapshot

### 4. 修复并行执行暴露的真实系统问题

系统级运行暴露并修复两个关键问题：

#### 并行 Ledger 写入不安全

问题：多个节点并行写 `state.yaml` / `manifest.yaml` 时，可能读到半截 YAML 或覆盖彼此写入。

修复：

- `runtime/ledger_transactions.py` 增加任务级锁
- `tools/ledger.py` 改为 atomic write：写临时文件、fsync、`os.replace`

#### 同一目标节点重复激活

问题：多个上游节点同一波指向同一 target role，例如 `senior-engineer`，会造成重复 activation/completion。

修复：

- `best_candidate_per_target`
- 同一 policy wave 每个 target role 只保留最高权重候选
- 运行状态中已完成/已执行节点进入 settled target，避免重复派发

### 5. 本地 CLI 入口

新增：

- `tools/langgraph_run.py`

可直接启动一次 Silicon Org 运行：

```bash
python3 tools/langgraph_run.py \
  --task-id task-local-demo \
  --description "Build a feature..." \
  --max-role-executions 8 \
  --replace
```

默认 runner 是 `semantic_command`。

### 6. Semantic node executor

新增：

- `tools/semantic_node_executor.py`

用途：把 LangGraph 调度出来的节点 invocation package 交给本地语义 agent 执行。

当前默认：

```bash
SILICON_ORG_NODE_AGENT=pi
```

也支持：

```bash
SILICON_ORG_NODE_AGENT=codex
SILICON_ORG_NODE_AGENT=claude
```

当前策略：先用同一个 runtime/default 模型执行所有节点。未来再通过 `org/models.local.yaml` 为每个节点单独配置模型。

`semantic_node_executor.py` 负责：

- 读取 `SILICON_ORG_INVOCATION_JSON`
- 读取 `SILICON_ORG_INVOCATION_PROMPT`
- 调用本地 agent CLI
- 要求返回 JSON
- 校正 Context Compression Report 的常见格式偏差
- 输出 artifact + context report 给 Ledger

### 7. 系统级验证

新增：

- `tools/org_system_validation.py`

这不是测试 LangGraph 本身，而是测试 Silicon Org 接入 LangGraph 后的组织行为：

- Context Compression Report

## 真实变化

旧 runtime 的主要问题：

- Runtime 容易手动挑节点，覆盖 graph propagation
- trigger/may_trigger/evaluator 边大量遗漏
- artifact approval 容易被人工伪造
- Ledger manifest 字段不完整
- learning signal 可能为 0
- Context Compression Report 没有稳定进入每个节点完成条件
- 并行运行没有被系统级验证压过

新版本的改善：

- 节点激活由 Policy 每波读取 weighted graph 动态计算
- LangGraph 负责 durable control loop 和 dynamic send
- Ledger 成为事实源
- 每个节点完成必须有 artifact + context report
- Graph Topologist 和 Learning 成为 delivery 后固定阶段
- 并行写入有锁和 atomic write
- 系统级验证进入 CI
- semantic executor 成为默认业务入口

## 当前边界

仍然不是终局：

1. 真实节点执行已经接入本地 agent CLI，但还没有完成每节点独立模型配置。
2. `semantic_node_executor.py` 现在做了 Context Report 格式校正，这是必要的工程护栏，但未来应逐步让节点 prompt 输出天然合规。
3. 系统验证仍设置 `max_role_executions`，用于防止无界传播。真实业务运行需要按任务类型配置合理收敛策略。
4. 当前默认同一模型执行所有节点。下一步才是按 role/model_profile 配置不同模型。
5. `codex` CLI 在本机当前版本遇到模型版本不兼容，默认改用 `pi`。这不是组织架构问题，是本地 agent CLI 状态问题。

## 使用方式

安装本地 OSS runtime：

```bash
python3 -m pip install -e '.[langgraph-oss]'
```

运行 Silicon Org：

```bash
python3 tools/langgraph_run.py \
  --task-id task-example \
  --description "Implement the requested software change" \
  --max-role-executions 8 \
  --replace
```

指定本地 agent：

```bash
SILICON_ORG_NODE_AGENT=pi python3 tools/langgraph_run.py --description "..."
SILICON_ORG_NODE_AGENT=codex python3 tools/langgraph_run.py --description "..."
SILICON_ORG_NODE_AGENT=claude python3 tools/langgraph_run.py --description "..."
```

系统级验证：

```bash
python3 tools/org_system_validation.py
```

## 收尾结论

这次开发把 Silicon Org 从协议设计推进到了一个可运行的软件工程组织运行时：

```text
Graph defines organizational law
Policy judges activation
LangGraph executes durable control flow
Ledger records facts
Context Block preserves intent
Semantic executor runs nodes
Topologist + Learning improve the org
```

下一阶段不应该再继续争论 LangGraph 是否进入系统。它已经进入。下一阶段应该直接在真实代码开发任务上使用 Silicon Org，并用 trace/learning 继续修正组织结构。
