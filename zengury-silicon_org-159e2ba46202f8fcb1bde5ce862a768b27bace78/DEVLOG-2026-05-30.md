## Key Design Decisions

1. **`may_trigger` conditions are structural, not semantic.** The text like "architecture includes user-facing frontend" is documentation. Gating must be explicit (`activation_task_types`). Without this, the graph activates UX nodes for backend refactors — 29 edges had no gating.

2. **pi subprocess is the bottleneck.** 80% of task time is in two pi nodes. DeepSeek API is 10-50x faster for analysis. Only implementation nodes need pi's full tool chain.

3. **Learning must be closed-loop.** Writing `learning.yaml` to trace is observation, not learning. The weights in `ontology/relations.yaml` must actually change for the organization to improve.

4. **Harness and nodes.yaml must agree.** api-designer's harness said `api-design-reviewer` while nodes.yaml said `senior-backend` — the contradiction made every run unpredictable.

## Remaining Known Issues

- pi subprocess speed (5-15 min per code-writing node) — architectural, not bug
- DeepSeek API occasional network drops — retry mitigates but doesn't eliminate
- HRBP scoring on elapsed time doesn't work for resume (timestamps lost in dry-run replay)
- `silicon_task.py` doesn't auto-detect task_type from description (needs NLP classification)
- No checkpoint persistence across process restarts (MemorySaver only)
